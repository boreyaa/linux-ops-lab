# 第六周复盘

## 一、这一周做成了什么

第六周把工具从"能采集"推到"能判断、能出报告"。三类东西落地：

- 检测器骨架：`detectors/base.py` 定死 `match()` 接口与四字段结果格式，`detectors/__init__.py` 集中登记，主程序遍历调用。
- 两类检测器：`ueditor.py` 查 UEditor 配置接口未授权，`sensitive.py` 查六条敏感路径（`.git/config`、`.svn/entries`、`.env`、`backup.zip`、`www.zip`、`phpinfo.php`）。
- 报告层：`report/tpl.html` 加 `report/render.py`，按高危、中危、低危、信息排序，输出单文件 HTML。

## 二、误报是怎么防的

两个检测器都不是只看状态码，而是双条件：状态码 200 且正文含该漏洞特有的内容标记。

- UEditor：正文必须出现 `imageUrlPrefix`、`imageMaxSize`、`imagePathFormat` 三者之一。
- 敏感文件：`.git/config` 必须含 `[core]`，`.env` 必须含 `=`，`phpinfo.php` 必须含 `PHP Version`。

这样做的原因是单页应用对任意路径都返回 200 加同一份首页，只看状态码会把每个路径都报成漏洞。

## 三、一次真实的对照实验

本次实测在 192.168.88.100 上跑完整流程，检测器命中 0 条。为确认"0 条"不是漏报，做了一次对照实验，构造三种响应喂给 UEditor 检测器：

| 构造的响应 | 检测器判断 |
| --- | --- |
| 200 + 首页正文 `<html><body>Welcome to nginx</body></html>` | 不命中 |
| 200 + `{"imageUrlPrefix":"/ueditor","imageMaxSize":2048000}` | 命中 |
| 404 + `Not Found` | 不命中 |

结论：检测器对"全站 200 但内容是首页"这种最常见的误报来源判为不命中，对真正的配置响应判为命中。这说明命中 0 条是靶机上确实没有 UEditor，不是判断逻辑失灵。

## 四、最后跑了什么

命令：`.venv/bin/python main.py --targets targets.yaml --out reports/`

结果：退出码 0，扫出 22/ssh、3306/mysql、8080/nginx 三个端口，指纹为 `200 nginx/1.18.0`，检测命中 0 条，生成 `reports/scan_20261118_111427.json` 与 `reports/report_20261118_111427.html`。

## 五、这一周没做的事

本轮没有在真实目标上捕获到误报，因此无法写"报了什么、复核后改了什么条件"的完整案例。防误报机制是设计时内置的双条件判断，并用上面的对照实验验证了边界。若后续在真实目标上遇到误报，按同样方式记录：报了哪条、手工复核看到什么、在判断条件里补哪一项特征。
